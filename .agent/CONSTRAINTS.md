# Constraints — What You Must Never Do

These rules are absolute. Violating them can cause security breaches, data loss, or broken production.

---

## 🔴 Security Constraints

### NEVER return the `password` field
Any code path that returns a user object **must** strip the password:
```typescript
// ✅ Correct
const { password: _, ...safeUser } = user;
return safeUser;

// ❌ Wrong — leaks hashed password to client
return user;
```

### NEVER store tokens in localStorage or response body
Access and refresh tokens must **only** be set in `httpOnly` cookies. They must never appear in the JSON response body where JavaScript can read them.

### NEVER skip token version validation on refresh
The `tokenVersion` check in `refreshTokens()` is the invalidation mechanism. Removing or bypassing it breaks the logout-all-sessions feature.

### NEVER use plain-text passwords
Always use `bcrypt` with a cost factor of 10:
```typescript
const hash = await bcrypt.hash(password, 10);
```

### NEVER trust user-supplied IDs for ownership checks
If an endpoint modifies a resource, verify the resource belongs to `currentUser.id`, not just the `id` in the request params.

## 🔴 Database Constraints

### NEVER run `prisma db push` on the main database
`db push` bypasses the migration history and can corrupt the migration state. Only ever use:
- `prisma migrate dev` (development)
- `prisma migrate deploy` (production/CI)
- `prisma db push` is only allowed on the **test database** (`vemtap-affiliate-test`).

### NEVER hand-edit migration SQL files
Migration files in `prisma/migrations/` are generated by Prisma. Editing them manually can cause drift. If you need a custom migration, create an empty migration and write SQL there explicitly.

### NEVER use `Float` for monetary values
Floating-point arithmetic causes rounding errors in financial calculations. Use `Decimal` in Prisma schema and `Decimal.js` or string arithmetic in code.

### NEVER delete Prisma migration files
Migration history is append-only. Deleting a migration file will break `migrate deploy` in any environment that hasn't applied it.

---

## 🔴 Build & Package Manager Constraints

### NEVER run `pnpm build` unless explicitly requested
The dev server (`nest start --watch`) is always running. Building creates unnecessary overhead.

### NEVER use `npm` or `yarn`
This project uses pnpm workspaces. Using npm or yarn will corrupt the lockfile.

### NEVER install packages at the repo root for API-specific dependencies
Feature packages belong in `apps/api/package.json`. Shared tooling (e.g., TypeScript, Prettier) belongs at the root.

---

## 🟡 Code Quality Constraints

### Never bypass `ValidationPipe` with `any` types on DTOs
All controller inputs must be typed DTOs. Using `any` removes input validation.

### Never use `console.log` for production logging
Use NestJS `Logger` service for structured logging:
```typescript
private readonly logger = new Logger(MyService.name);
this.logger.log('User created', { userId });
this.logger.error('Failed to process', error.stack);
```

### Never import `PrismaService` directly into a controller
Controllers must never access the database directly. Business logic and data access belong in services.

### Never put business logic in a DTO
DTOs are data shapes with validation decorators only — no methods, no logic.

### Never use raw SQL via `prisma.$queryRaw` for standard CRUD
Use the Prisma query API (`prisma.user.findMany()`, etc.). Raw SQL is only acceptable for complex aggregations that Prisma cannot express.

---

## 🟡 Testing Constraints

### Never test against the main `vemtap-affiliate` database
E2E tests use `vemtap-affiliate-test`. The `create-test-db.ts` script drops and recreates it fresh.

### Never mock `PrismaService` in E2E tests
E2E tests talk to a real PostgreSQL database. Mocking Prisma there defeats their purpose. Use mocks only in **unit tests**.

### Never skip cleanup in E2E tests
`beforeAll` and `afterAll` hooks **must** delete all test data:
```typescript
beforeAll(async () => {
  await prismaService.user.deleteMany({});
});
afterAll(async () => {
  await prismaService.user.deleteMany({});
  await app.close();
});
```
